## 第二轮代码审查：修复结算/死亡/AI 解析类 bug（index.html）
上一轮修了"选人即崩"（缺失 BK/bhOn 等函数）。本轮聚焦上次无头测试未跑到真值的 AI/死亡路径，新增发现并修复：

1. **选项可重复点击结算（致命玩法 bug）**：出结果后 `event-panel` 不隐藏，玩家点第二个选项会再次扣加数值、重复写历史、曲线多一个点。修复：`makeChoice` 加 `currentEvent._resolved` 防护。
2. **被动健康衰减致死不触发结局（致命逻辑 bug）**："健康=0 皇帝驾崩"只在选项结算后检查；自然衰减磨到 0 时无人检查，皇帝不死、游戏无限续。修复：`nextMonth` 被动衰减后对 `state.stats.health<=0` 调用 `endGame("驾崩")` 并 return。
3. **驾崩竞态**：死亡靠 1200ms 定时才置 `cohEnded`，其间点"推进下月"仍可死后续玩。修复：`renderOutcome` 死亡分支**同步**置 `cohEnded=true`（结局屏仍延迟 1200ms 显示）；另给 `endGame` 加 `if(cohEnded) return` 防多路径重复进入。
4. **AI JSON 解析脆弱**：模型用 ```` ```json ```` 围栏或前后加说明文本时 `JSON.parse` 直接抛错，每次 AI 生成都静默降级成预设事件。修复：新增 `safeParseJSON`（去围栏 + 截取首尾 {} / []），`callAI` 改用之。
5. **fetch 超时未清除** + **choices 容错**：`callAI` retry 循环把 `t` 提到 try 外并在 catch 清 `clearTimeout(t)`；`loadEvent`/`pregenerateMonths` 对 AI 返回的字符串型 choices 兜底为 `{text, hint}`。

## 修复「首回合显示文言文、次回合才白话文」
用户反馈：进入游戏后第一回合（事件）仍是文言文，第二回合起才白话文。

### 根因
- 首回合是「历史事件」预设（`enterMonth` 在 month=1 命中 `reignStart` 年事件 → `buildHistoricalEvent` 设 `currentEvent._ev=hit`），`renderEvent` 用 `bhEventSync(emp, hit)` 查 `emp.baihua.events[hit.id]`。
- 当时 `coh_data.js`（游戏实际加载文件）未含白话层（全量翻译被中断，仅 43/262 皇帝译好）→ 查不到 → **先渲染文言文、再异步补译**（renderEvent 旧逻辑先 paint 原文再 `bhFetchEventBaihua` 异步 patch）。
- 第 2 回合及以后多为 AI 生成事件，`PROMPTS` 在 `settings.baihua` 开启时强制 AI 用现代白话输出，故直接是白话——形成「首回文言、次回白话」的对比。

### 修复（index.html）
- `renderEvent` 重构为三分支，**白话模式下绝不先闪文言文**：① `bhEventSync` 命中→直出白话；② `bhOn() && currentEvent._ev && aiAvailable()`（仅预设数据事件缺译）→ 先「白话文生成中…」占位、译出即替换；③ 其余（AI 生成事件本身已是白话 / 离线无 AI）→ 直接渲染 currentEvent 原文。
  - 关键：等待补译分支**限定 `currentEvent._ev` 存在**，避免把本就是白话的 AI 事件误判为需补译而闪「生成中」（防回归）。
  - 新增 `_evSeq` 序号守卫：异步补译回写时 `if(seq===_evSeq)` 才应用，防止过期异步覆盖新事件。
  - `bhFetchEventBaihua`/`bhFetchField` 加 `onErr` 兜底：补译失败/空结果时回退 `paintEventRaw`（显示原文），避免永久卡「生成中」。
- `selectEmperor` 导入界面同步修复：新增 `fillBaihuaField`，顶层字段（评价/背景）在白话模式无层且联网时先「生成中」再即时替换，离线/失败回退原文，避免「第一次进入」时闪文言文。

### 验证
- 抽取真实函数 + 桩 DOM 跑四场景仿真：S1 预设缺译→生成中后补译、S2 预设有层→直出白话、S3 AI 事件→直出白话且不触发补译（无回归）、S4 离线预设→保留原文，全部 PASS；`_evSeq` 守卫防串台验证通过。
- `node --check` 整段内联脚本语法通过。

### 配套（进行中）

## 审计+修复「科技属性加点→科技归零/负值不得触发驾崩或惩罚」（用户需求）
用户要求：科技加点致科技值降为 0/负时，不得触发驾崩或任何生命/状态/剧情惩罚。

### 审计结论
- **当前代码本就安全**：驾崩（死亡）唯一触发是 `state.stats.health<=0`（`renderOutcome` 与 `nextMonth`）；科技在所有写入路径均 `clamp(...,0,100)`，永不为负；`detectCrisis`（五维）刻意排除 tech；唯一科技相关"负面"事件是「科技阻力」，触发条件是科技**过高**（>initStats.tech+20 且有越代科技），偏低时 `shouldTriggerTechResist` 直接 return false。
- 唯一隐患：`nextMonth` 的「长期低位崩盘」会选最低非健康项施 -2，原筛选仅排除 health，可能把归零的科技选为"最弱项"（结果 clamp 到 0 无实际变化，但语义上属惩罚）。

### 改动（全部 index.html）
- `nextMonth` 长期低位崩盘：筛选条件由 `k!=="health"` 改为 `k!=="health" && k!=="tech"`，科技永不被选为惩罚对象；若科技最低则改罚次低国力项。
- 在 `researchTech`（扣 tech 处）、`recomputeTechProfile`（增量注入处）、`detectCrisis`（危机五维处）补注释，固化"科技∈[0,100]，归零仅无效、绝不触发死亡/惩罚"的不变量，防回归。
- 语法校验：主 inline 脚本（~135KB）`new Function` 通过（此前报的 SYNTAX_ERROR 是提取正则误匹配 HTML 注释内字面 `<script` 所致，非真实问题）。

### 不变量（后续勿破）
- 科技值恒由各处 clamp 保证 ≥0；任何新增判定都不得把 `tech<=0`/`tech<0` 当作危机/死亡/惩罚条件；`detectCrisis` 的items 数组不得加入 tech。
